# 記録からハーネスを改善する

1. `harness/records/pr-*.md` を読み、分類、出どころ、根拠を整理する。
   不明・未実施を成功や指摘 0 件として数えない。
2. 人・bot・CI に届いた指摘と内部検証で捕まえた指摘を分ける。
   同じ根拠の重複を除き、前回の対策後も繰り返している問題を探す。
   記録が少なければ、根拠不足と報告し、仮想の失敗を補わない。
3. 介入先を 1 つ選び、何を止めたいかと代償を説明する。
   - 機械的に確定できるものは検査へ置く。通る例と止める例を用意する。
   - 設計判断の基準は短い `rules/`、レビュー時だけ必要な観点は `.claude/agents/` へ置く。
   - リポジトリ固有の実例は `harness/case-law/` へ置き、根拠の PR と判断の分かれ目を残す。
   - 作業の順序や取得忘れは該当するスキルへ置く。
4. 追加前に重複・矛盾・不要な規約を削る。`AGENTS.md` と `rules/*.md` の 200 行上限を
   上げて通さず、必要時だけ読む文書へ移す。
   Swift の構文を正規表現だけで lint しない。
5. 計画と差分を該当レビュー定義で検証し、
   `bash harness/githooks/pre-push` と変更に関係する検証を実行して改善 PR を出す。
   どの記録が根拠で、どの失敗を検出し、何を判定できないかを PR に残す。

過去の記録は変更しない。成功した回の装置まで増やさず、使われない観点や過剰な手順も削る。
構成と検査の限界は [harness/README.md](../../../harness/README.md) を参照する。
