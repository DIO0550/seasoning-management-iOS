# 実装を進める

ユーザーの依頼を受けるメインエージェントを親とし、親がオーケストレーターを務める。
各担当の定義を実際に読み、委譲時に内容を渡す。Claude の `tools` 設定が他環境でも自動適用されるとは扱わない。

1. 親は `AGENTS.md`、`rules/`、該当仕様、Issue と既存の差分を読む。
   ユーザーとの会話と外部情報の取得は親が担当し、必要な情報を担当へ渡す。
2. 親は [planner](../../agents/planner.md) へ依頼、完了条件の候補、対象 Issue・仕様、既存の差分と調査範囲を渡す。
   planner は読み取り専用で、完了条件・対象外・変更ファイルと理由・方針と根拠・検証・未確定事項を返す。
   親は計画を確認する。実装は 1〜2 ファイル程度を目安にし、不可分の設定・テスト追加は理由を示す。
3. 親は [plan-reviewer](../../agents/plan-reviewer.md) へ計画、依頼と完了条件、仕様・コードの参照先を渡す。
   レビュー役は定義に従って指摘と未確認事項を返す。親は根拠を確認し、必要な指摘を planner へ差し戻す。
   計画の問題を解消した後に親が採用し、計画と却下案を既存 Issue、直接の依頼なら PR 本文へ残す。
   通常の実装判断で新しい承認待ちを作らず、既に依頼された作業を進める。
4. 親は [implementer](../../agents/implementer.md) へ採用済みの計画、完了条件・対象外、編集を許可するファイル、
   検証コマンドと既存の差分を渡す。実装担当は1人に限定し、親や他の担当は同時に編集しない。
   implementer は指定範囲を実装し、変更ファイル・完了条件の結果・検証コマンドと環境・終了コードと結果・
   未実施の理由・計画からの逸脱を返す。前提が崩れた場合や指定外の変更が必要な場合は親へ返し、範囲を広げない。
   iOS の実行は [harness/README.md](../../../harness/README.md) の Mac / Xcode 手順に従う。
5. 親は最終差分、完了条件、関係する仕様と検証結果を [swift-reviewer](../../agents/swift-reviewer.md) と
   [test-reviewer](../../agents/test-reviewer.md) へ渡す。Swift を変えない場合は該当観点だけ使う。
   レビュー役には編集・Git 操作・通信を許可せず、定義に従って根拠のある指摘と未確認事項を返してもらう。
   親が根拠を確認し、必要な修正と許可ファイルを implementer へ渡す。修正後は影響する検証とレビューを再実施する。
   テストを増やすこと自体を目的にせず、計画を見直す必要があれば planner と計画レビューへ戻る。
6. 親は差分を統合して `git status` と差分を確認し、`bash harness/githooks/pre-push` を実行する。
   レビュー結果を受け取り、スクリプトの終了コードで判定した後、対象ファイルだけコミットして PR を作る。
   Git の変更操作・commit / push・PR 作成は親が担当する。既存 Issue がある場合は `Closes #番号` を書く。
7. 親は PR に変更の目的、結果、実行した検証と未実施の理由を記す。
   CI とレビューの状態を確認し、届いた指摘も根拠を確認して implementer へ渡す。
   未完了・環境待ちのチェックがあれば、状態を明示して引き渡す。
8. 親はマージを確認した後の記録依頼で [harness-record](../harness-record/SKILL.md) を使う。
   PR 作成だけの依頼では自動マージしない。

サブエージェントは再委譲・Git の変更操作・外部通信を行わない。
サブエージェントを使えない環境では親が各定義に従って代行し、委譲できなかった役割と自己レビューを PR と最終報告に記す。
検証後に親が `git status` を確認し、意図しない変更があれば混ぜずに調べる。実行できない検証を成功と報告しない。
