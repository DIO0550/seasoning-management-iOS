# 実装を進める

1. `AGENTS.md`、`rules/`、該当仕様、Issue と既存の差分を読む。
   完了条件、今回扱わないこと、既存実装を区別する。
2. 変更予定のファイルと検証を計画する。独立してマージできる変更を分ける。
   実装は 1〜2 ファイル程度を目安にし、不可分の設定・テスト追加は理由を示す。
   計画と却下案は既存 Issue へ、直接の依頼なら PR 本文へ残す。
3. [.claude/agents/plan-reviewer.md](../../agents/plan-reviewer.md) の観点で計画を検証する。
   別エージェントが使えれば読み取り専用で渡す。使えなければ定義を読んで自己検証する。
   新しい承認待ちを作らず、既に依頼された作業を進める。
4. 必要な実装だけを行い、変更に適した検証を実行する。
   iOS の実行は [harness/README.md](../../../harness/README.md) の Mac / Xcode 手順に従う。
5. 最終差分を [swift-reviewer](../../agents/swift-reviewer.md) と
   [test-reviewer](../../agents/test-reviewer.md) の観点で検証する。
   Swift を変えない場合は該当観点だけ使い、テストを増やすこと自体を目的にしない。
   検証役へ差分と完了条件を渡し、編集・Git 操作・通信を許可しない。
   指摘の根拠を確認して直し、修正が影響する検査を再実行する。
6. `git status` と差分を確認し、`bash harness/githooks/pre-push` を実行する。
   スクリプトの終了コードで判定し、対象ファイルだけコミットして PR を作る。
   既存 Issue がある場合は `Closes #番号` を書く。
7. PR に変更の目的、結果、実行した検証と未実施の理由を記す。
   自己検証ならその旨を記す。CI とレビューの状態を確認し、届いた指摘を修正する。
   未完了・環境待ちのチェックがあれば、状態を明示して引き渡す。
8. マージを確認した後の記録依頼では [harness-record](../harness-record/SKILL.md) を使う。
   PR 作成だけの依頼では自動マージしない。

検証エージェントの結果を受け取るまではコミットしない。検証後に `git status` を確認し、
意図しない変更があれば混ぜずに調べる。実行できない検証を成功と報告しない。
