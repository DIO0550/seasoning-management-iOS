# テストと検証

- 単体テストは `SeasoningManagerTests` の Swift Testing、UI は `SeasoningManagerUITests` の XCTest に置く。
  iOS アプリを Linux の `swift test` で検証できる前提にしない。
- 実装手順や内部のプロパティ配置ではなく、入力に対する結果・エラー・保存後の状態を確かめる。
  正常系だけでなく、変更が影響する境界・不正入力・未設定を選ぶ。
- ケースの差だけなら `@Test(arguments:)` を使う。テスト内の条件分岐で検証をスキップしない。
- 保存モデルは実際の `ModelContainer` / `ModelContext` で確かめる。
  再起動後の保持や移行を扱う変更は、メモリ内の検証に加えてストア再読込を確認する。
- テストごとにデータを隔離する。時計・UUID・ファイル・非同期完了に依存するテストを偶然のタイミングで通さない。
- 型・JSON・ドキュメントなどの低影響変更には実装をなぞるだけのテストを足さない。
  フックや検査を変更する場合は、通る例と止める例を実行する。
- Swift を変更したら [swift-format の手順](../harness/README.md#swift-の整形とlint)で `python3 harness/swift-format.py lint` を実行する。
  実ツールを使えない環境では未実施として報告し、専用 CI の結果を確認する。
- UI の確認では空状態、主操作、キャンセル、入力保持、失敗時の表示のうち変更に関係するものを選ぶ。
- PR には実行コマンド・終了結果・環境・未実施項目を書く。配置検査、単体、UI、実機、同期を混同しない。
