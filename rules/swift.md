# Swift の書き方と責務

## 型と振る舞い

- 値を表す型は `struct` / `enum` を基本とし、参照の同一性やフレームワークの要求があるものは `class` を使う。
  SwiftData の `@Model final class` や XCTest のテストクラスに値型化を強制しない。
- 判定・計算・不変条件は、その意味を持つ型のメソッド・計算プロパティへ置く。
  型を増やすこと自体を目的にせず、保存操作に属する検証は保存境界へ置く。
- `caseless enum + static` は所有者となる型がない純粋関数・定数の名前空間に使える。
  型に属する振る舞いを `Helper` / `Utils` へ逃がすために使わない。
- `static` 自体を禁止しない。時計・通信・保存などの副作用を static の裏に隠さず、必要な依存を引数などで渡す。
- 状態の有限集合は `enum`、失敗は `throws` などの明示的なエラー、不在は Optional で表す。
  失敗を `nil`・0・既知の状態へ変換して成功扱いしない。

## 境界・protocol・SOLID

- 設計は責務の境界から考え、公開する契約（入力・結果・失敗・不変条件・actor）を決めて実装する。
  業務判断が UI・SwiftData・OCR・通信の具体的な仕組みに依存しない方向を保つ。
- 境界で差し替える振る舞いは、利用側が必要とする小さな `protocol` として定義する。
  実装が1つでも依存の隔離が必要なら採用する。すべての型に機械的に protocol を付けない。
- 純粋な計算や閉じたデータは具体的な値型で扱える。依存が単一の操作ならクロージャによる注入も選べる。
  protocol・ジェネリクス・`some` / `any` は、必要な契約と型情報の扱いに合わせて選ぶ。
- **S / 単一責任**: 変更理由が異なる業務判断・画面状態・外部アクセスを分ける。
- **O / 開放閉鎖**: 変化する実装を境界で追加できるようにする。有限の状態集合は enum で明示する。
- **L / 置換可能性**: 実装を替えても入力条件・結果・失敗・副作用・actor の契約を守る。
- **I / インターフェース分離**: 利用側が使わない操作を要求する大きな protocol を作らない。
- **D / 依存性逆転**: 業務方針は必要な契約に依存し、保存・OCR・通信の実装を外側から注入する。
  SOLID は契約と変更の波及を判断する基準とし、型や層を増やすこと自体を目的にしない。

## 読みやすさ

- 変更しない値は `let`。公開範囲は必要最小限にし、命名は業務上の意味と単位を表す。
- 通常の関数では `guard` や早期 return で条件を分ける。`guard ... else` は当然使ってよい。
- if と同じ行に return を書かず、三項演算子をネストしない。
  長い `||` の列挙は意味のある判定や `switch` へ分け、処理のまとまりの間に空行を入れる。
- 深い分岐は責務で分割する。行数・ネスト数を減らすためだけの一度きりの抽象化は増やさない。
- 本番コードの `!` / `as!` / `try!` は避ける。`try?` は失敗を無視してよい理由がある場合だけ。
  回復可能な入力・保存失敗を `fatalError` で処理しない。

## 戻り値と並行処理

- `@discardableResult` は、戻り値を無視する呼び方も正当な API にだけ付ける。
  検証結果・保存結果を見落とした警告の回避には使わない。
- actor の境界はプロジェクト設定も確認する。`Task` を作っただけでバックグラウンド処理とみなさない。
- UI と `ModelContext` の所有・更新場所を明示し、actor を越える処理へ可変の保存モデルを無造作に渡さない。
  `@unchecked Sendable` や `nonisolated(unsafe)` で警告を消さず、値の受け渡しを見直す。
