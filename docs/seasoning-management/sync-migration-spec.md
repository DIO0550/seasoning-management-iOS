# iCloud 同期・既存データ移行仕様（端末側の処理）

> [概要](./index.md) / [データモデル](./data-model-spec.md)

## 同期の目的と対象

端末内の SwiftData を編集の起点にして、同じ iCloud アカウントを使う端末間で商品、商品画像、個体、使い切り履歴、削除を同期する。独自サーバーやアプリ専用アカウントは設けない。SwiftData の CloudKit 同期に必要な iCloud・Background Modes の設定と、同期対応スキーマの検証を行う。現在の entitlements は CloudKit コンテナ識別子が空であり、同期は未検証である。

商品名・賞味期限の[OCR](./ocr-spec.md)は端末上で実行する。読み取りに使っただけの画像と未確定候補は保存・同期しない。利用者が確定して保存した商品名・賞味期限だけを通常のデータとして同期する。商品画像として明示的に選んだ画像は従来どおり同期対象とする。

| 状態 | 利用者に見える振る舞い |
|:--|:--|
| 接続中 | ローカルで登録・編集・削除でき、変更を同期する。 |
| オフライン・一時的な同期失敗 | ローカルの操作を継続し、変更を保留して接続後に再試行する。同期中・保留・失敗を区別して表示する。 |
| iCloud 未サインイン・利用不可 | ローカルの操作を継続できる。同期できない理由と、再接続時の扱いを示す。 |
| 別端末から変更 | ローカルの一覧・詳細へ反映する。同じ ID の二重表示を作らない。 |

ローカル保存成功とクラウド反映完了は別の状態として扱う。同期失敗をローカル保存失敗として見せない。

### 現状と設計上の判断

現在の Product / Item は業務 ID と `updatedAt` を持つが、変更の版・削除記録・独立した所属商品 ID は持たない。商品と個体の関係は Optional、両方向の削除規則は `.nullify` で、通常起動は `.none` により同期を無効にしている。`CloudSchemaTests` はスキーマと保存の確認用で、競合の解決・削除優先・複数端末間の整合性を実装していない。

従来の「レコード単位で更新日時の新しい変更を採用」は、端末時計や自動同期の採用順から保証できないため、以下の検証案では**確認済みの版を基にした変更を優先し、同時編集は両方を保全して利用者が確認できる**ルールへ具体化する。[データモデル](./data-model-spec.md)の `updatedAt` の「同期競合判定用」は、この案を採用する場合には表示・診断用途へ変更する必要がある。まだモデルや他仕様の確定変更は行わない。

| ケース | 検証に採用する方式 | 利用者に見える結果 |
|:--|:--|:--|
| 同じ商品・個体の同時編集 | 編集ごとに不変の版を追記し、親の版 ID で因果関係を判定。競合候補を保持し、全端末で同じ規則で暫定版を選ぶ。 | 競合があることを示す。候補を確認して保存すると、両方を親とする解決版を追加する。 |
| 個体の削除と編集 | 対象 ID に対する不変の削除記録（tombstone）を別に追加。編集版より削除記録を優先する。 | 削除記録受信後は在庫・履歴から除外。編集途中の内容は退避して理由を示し、同じ ID で再作成しない。 |
| 商品の削除と編集（個体なし） | 商品削除要求を追記して論理的に非表示にする。後述の個体競合がない限り、商品編集で要求を解除しない。 | 削除保留中と示す。本文・画像を物理削除せず、編集による自動復活を防ぐ。 |
| 商品削除と別端末の個体追加 | 削除前に全状態の個体を検査。遅着個体を検出したら削除要求の却下記録を追記し、商品を保持する。 | 商品削除を確定せず「別端末で個体が追加されたため削除できません」と表示。個体を失わない。 |

この判断はアプリ層の設計であり、CloudKit が提供する削除優先ポリシーではない。同じ論理 ID に属する全記録が届いた後の収束を目指す。まだ届いていない削除・個体を端末が即時に検知できるという保証は置かない。

### 自動同期で扱える範囲

| 箇所 | できること・検証対象 | この方式で前提にしないこと |
|:--|:--|:--|
| ローカルの保存直前 | 入力・状態・日付・既知の削除記録・個体件数を検査し、処理を直列化して版とローカル表示を保存する。 | 他端末の未到着操作の検知。ローカル保存の成功による全端末の削除可否の確定。 |
| SwiftData の自動 CloudKit 同期 | Core Data の `NSPersistentCloudKitContainer` による転送・標準競合処理を使う。 | `updatedAt` による業務ルールの自動実装、全属性が必ず一方の編集内容にそろう保証、任意の競合処理を差し込める公開コールバック。調査した公開 API ではその介入点を確認できていない。 |
| 取り込み後の整合性確認 | History API / 再 fetch を使い、到着した版・削除・参照を再評価する。History のトークンはストア別に管理する。 | History のトークンを端末間共通の版として比較すること、クラウドで失われた競合候補を History から必ず復元すること。 |
| 関係の取り込み | Optional の関係が未解決なら通常表示を保留し、後で再検査する。 | 関係の一括・順序どおりの到着、`.deny` や一意制約による全端末の整合性保証。 |
| CloudKit を直接使う別方式 | 独自管理レコードなら保存条件・競合エラーを扱う設計を別途検討できる。 | SwiftData 管理下の内部レコードを直接書き換えて自動同期に介入すること。同一ストアを2種類の同期処理に管理させない。 |

Apple の WWDC19 資料は標準処理を last-writer-wins と説明し、同時編集の保全には別々の寄与を記録するモデルを紹介している。ただし、その説明だけで対象 OS / SDK の勝者や粒度を断定しない。SwiftData の公開資料は関係処理の非原子性・不定順序を示している。以下の追記方式はこれらを踏まえたアプリ独自の案であり、実データ量・画像転送量を含めて検証する。

### 版と削除記録の最小設計案

モデルの追加・保存処理・画面への接続は後続の小さな変更に分ける。現在の Product / Item を上書き同期するまま、日時だけを比較する実装には進まない。

- 編集版は `revisionID`、対象の種類と業務 ID、親の版 ID 群、論理カウンター、検証済みの全業務値を持つ。個体版には関係とは独立した `productID` を保持する。画像はその版が指す不変の画像 ID で対応づけ、到着前は読み込み待ちとする。画像の複製・容量コストは別途測定する。
- 編集元の親は、フォームを開いた時点の版から引き継ぐ。保存時に未確認の最新の版へ付け替えない。保存済みの版は変更せず、別端末の編集と同じ同期レコードを上書きしない。
- 子孫が到着した版は候補から外す。未解決の複数の末端版がある場合、`(論理カウンター, revisionID の正規化した文字列表現)` の辞書順で最大の版を暫定表示する。カウンターは対象について既知の最大値＋1、同端末では直列に発行し、再起動後も永続記録から復元する。これは実時間の新旧を表さない。競合候補は消さず、解決版は確認した全候補を親にして追加する。
- 状態・開封日・使い切り日、栄養素と基準量などは同じ版の全値として採用する。別版の属性を混ぜない。親が未到着・循環・値が不正な版は通常表示せず保留し、理由を記録する。不正な版を既定値で救済しない。
- 個体削除は本文とは別の追記専用記録とし、`operationID`、対象種類・ID を保存する。既知の削除記録が1件でもあればどの編集版にも優先する。単一の `isDeleted` / `deletedAt` を編集と一緒に上書きする方式ではない。削除前の編集候補も当面保全する。
- 再送は同じ操作 ID を使う。一意制約に頼らず、同一 ID・同一内容は投影時に1件にまとめる。同一 ID なのに内容が異なる記録は整合性エラーとして隔離する。表示から同期レコードを再生成しない。
- 同期する記録を正とし、Product / Item の表示用状態は再構築可能なローカル投影とする。投影を再度クラウドへ同期して循環させない。異なるストア間では SwiftData のリレーションを張らず、業務 ID で照合する。投影完了後に処理済みトークンを保存し、途中失敗時は同じ記録を再処理できるようにする。
- 起動・前面復帰・変更検知時に再検査する。History のトークン失効や投影不整合時は全記録から再構築する。History の `.preserveValueOnDeletion` はローカル履歴の属性保全であり、ここでいう端末間で保持する削除記録の代わりにはしない。

### 商品削除と孤児防止

1. 商品削除を要求した端末は、商品 ID に属する未開封・使用中・使い切り個体を確認する。1件でもあれば拒否する。関係配列だけでなく独立した `productID` を持つ個体記録を照合し、未解決・不正な参照がある場合も削除を保留する。
2. 0件なら不変の削除要求を保存する。通常一覧から非表示にできるが、「削除保留中」と確認できる場所を設ける。商品本体・画像・ID は保持し、物理削除をしない。要求を知っている端末での新規個体追加は拒否する。
3. 要求を知らなかった別端末から削除されていない個体が届いたら、その要求 ID に対する不変の却下記録を保存する。却下が1件でもあればその要求は無効とし、商品と個体を表示可能に戻す。これは確定した削除の復活ではなく、保留していた要求の拒否として説明する。商品編集だけでは却下しない。
4. 却下後に個体が削除されても古い要求を再び有効にしない。利用者が改めて削除を確認し、新しい要求を発行する。複数の要求がある場合も、それぞれ検査し、生存個体があれば全て拒否する。
5. 個体の所属商品が未到着なら在庫・履歴・件数の通常表示から保留し、保留件数を示す。商品到着後に再評価する。一定時間の未到着だけで孤児と断定して個体を削除したり、商品を仮名で再生成したりしない。解決しない場合は再試行と診断対象にする。

無期限にオフラインの端末を許す以上、自動同期だけで「今後個体が到着しない」と判定できない。この案では商品削除の全端末に対する確定・物理消去の期限を保証せず、削除記録・版・画像を初版では自動回収しない。これは既存の商品削除仕様に対する制約であり、確定時期や即時画像消去が必要なら、全書き込みを協調させる方式やオフライン時の操作制限を別途設計してから採用を決める。固定の待ち時間や1回の同期成功を確定条件にしない。

### 実機2台での検証手順

**現行アプリだけでは下表の採用案を実行できない。** 先に #21 の署名・Development コンテナ・同一テスト用 iCloud アカウントの設定を行い、既存モデルの標準動作を観測する。その後、追記版・削除記録・投影の試験用実装を別変更で用意し、同じケースを再実行する。両段階の結果を混ぜない。Production コンテナや実利用者のデータを使わない。

## 旧 Core Data アプリの保存データ移行

`old/src/SeasoningManager` の旧アプリが保存した `Seasoning` を、新しい SwiftUI / SwiftData アプリへの更新後も失わない。既存アプリとして更新できる識別子・署名・保存領域を維持し、旧 Core Data モデルで旧ストアを読み取ってから SwiftData の新ストアへ変換する。SwiftData の新モデルで旧ストアを直接開けると仮定しない。新しいXcodeひな形の `Item(timestamp)` は移行先ではない。

| 旧モデルの値 | 移行先とルール |
|:--|:--|
| 1件の `Seasoning` | 1件の Product と1件の Item に変換する。同名でも勝手に統合しない。 |
| `identifier` | 有効なら Item ID に引き継ぐ。欠ける・重複する場合は新しい一意な ID を割り当てる。 |
| `name`, `type`, `image` | Product へ引き継ぐ。名前・種類が欠損したレコードは元の値を端末内に保全して「修正が必要」に分け、修正後に Product / Item として取り込む。欠損の仮値を実データとして同期しない。 |
| `expirationDate` | Item へ引き継ぐ。 |
| `openingDate` あり | 日付を保持し、状態を `inUse` とする。 |
| `openingDate` なし | 状態を `unopened` とする。 |

既存データの移行は一度だけ、途中で失敗した場合は再実行しても個体を重複させない。移行前の保存データを破壊せず、移行完了を確認してから SwiftData の同期を開始する。新旧ストアの場所を分け、旧ストアを新しいひな形のコンテナで上書きしない。移行直後に商品が1件ずつ分かれていてもよい。商品統合は初版の自動処理に含めない。

移行テストでは旧版で保存した実データを用い、新版を上書きインストールして件数・画像・日付を確認する。新規インストールだけの動作確認では移行完了とみなさない。

修正が必要なレコードの件数と元の値を利用者に示し、名前・種類を補って取り込めるようにする。この処理が終わるまで、該当レコードだけを同期対象から外し、ほかの正常なデータの利用は妨げない。

`old/src/old` は別の試作コードであり、その保存領域の存在や旧 `SeasoningManager` アプリへの継承は確認できていない。この別試作アプリからの自動移行は別途調査する。

### 保存場所と読み取り条件

旧アプリは `NSPersistentContainer(name: "SeasoningManager")` を作り、保存 URL を変更せずに `loadPersistentStores` している。既定の保存先から推定される旧ストアは **`<アプリのデータコンテナ>/Library/Application Support/SeasoningManager.sqlite`** である。実端末の URL は未取得のため、旧版の `persistentStoreCoordinator.persistentStores` の各 `url` と実ファイルを照合して確定する。データコンテナの UUID を含む絶対パスは固定せず、更新後のコンテナ内で保存先を解決する。

Issue #15 の調査時点では新アプリはひな形の `Item(timestamp)` を使っていた。#20 反映後の対象ブランチは Product / 個体 Item と `cloudKitDatabase: .none` を使うが、保存 URL は依然として既定値で、旧ストアの読み取りは未実装である。移行実装時には新しい `ModelConfiguration.url` を記録し、旧ストアと異なる URL を明示する。既定のファイル名だけを根拠に安全と判断しない。

- 旧ストアが存在することを確認してから、旧 `SeasoningManager` モデルで読み取る。読み取り失敗時に空ストアを作って「移行成功」と扱わない。
- バックアップは書き込みを停止した整合的な状態で取得する。SQLite 本体だけでなく、存在する `SeasoningManager.sqlite-wal` / `SeasoningManager.sqlite-shm` と関連ファイルも保全する。稼働中に本体だけコピーしない。
- 更新でデータコンテナへアクセスできることと、旧モデルのレコードを読み取れること、新モデルへ変換できることは別々に検証する。

### 更新として配布する条件と自動移行できないケース

通常の更新では同じ Bundle ID を維持し、旧配布元の Team・App ID に対応する有効な署名を使用する。新旧の署名済み `application-identifier`（App ID Prefix を含む）と Profile の権限を照合する。Team 移管や Prefix 変更がある場合は Apple の移管手順を別途確認し、Bundle ID の一致だけで上書きできると判断しない。CloudKit・Push の権限も新しい Profile と整合させる。

App Store 配布済みなら同じ App Store Connect のアプリレコードへの更新とし、受理されるバージョン・ビルド番号を設定する。開発・Ad Hoc 配布なら対応する署名と端末登録などを確認する。実際の旧配布経路は未確認であり、その経路に合わせた更新を検証する。

| 条件 | 扱い |
|:--|:--|
| 同じアプリとして削除せず上書きし、旧データが残っている | 自動移行の候補。署名・旧ストア読み取り・変換の検証が必要。 |
| Bundle ID を変更して別アプリとして配布する | 別サンドボックスになる。現在の構成では旧コンテナを直接読めず、自動移行できない。同じ Team や同じ iCloud アカウントでも解決しない。 |
| 署名不整合で更新が拒否される | 署名を修正する。旧アプリを削除してインストールし直す方法を移行手順にしない。 |
| 旧アプリをデータごと削除済み、または別端末へ新規インストールする | 旧ストアがないためローカル自動移行はできない。復元可能なバックアップ等があれば別途扱う。 |
| 端末が新アプリの最低 iOS を満たさない | その端末では更新・移行を実行できない。 |

別アプリ配布を選ぶ場合は、旧アプリ側のエクスポートと新版側のインポートなど、利用者がデータを受け渡せる経路が別途必要になる。後から新アプリだけに App Groups を追加しても、旧アプリの私有ストアが共有領域へ移るわけではない。
